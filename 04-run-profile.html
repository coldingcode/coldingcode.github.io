§1composeProfile：五层拼齐

160

prepareProfile（98-103 行）：调 02 页的 loadProfile，然后重写空根配置。注释解释为什么每次都要重写：Loader 的树写回（插件自卸载会持久化当前树）可能把组合好的行烤进 cordis.yml——下次 boot 就会重复每个 bundle 的 insert。所以根永远是空的。

161

第③层：home 级 $DSH_HOME/cordis.patch.yml——机器级偏好，在 profile 层之后应用（高于它）。loadOptionalPatches：文件不存在就返回空（可选层）。

162

第④层：--patch overlay，按 argv 顺序。注意这里 overlay 只是被 load；真正 push 进 composedOverlays 是在 154 行复制之后——因为第⑤层遥测开关也要进 overlay，而用户 overlay 不能被污染。

165

五层压成一张表（只列前四层；第五层在 169 行并入）：同一个 composeEntries——与 boot 里的挂载用同一个算法，保证「flag 推导和配置 dump 看到的，就是实际挂载的」。

166

rows 是 id → Entry 索引，供 launcher 自己的行级检查（如 159 行查 agent-presets 是否存在）。

173-177

agent-presets 特例：SHIPPED_PRESET_ROOT（app 自带的预设目录，源码/产物两种布局下都在 app 旁边）只有这个 launcher 能解析，所以作为 overlay 推入。注释：「writable root 由 dsh-agent-presets 自己追加」，launcher 永不覆盖用户目录，只补系统目录。

182-183

第⑤层：遥测开关。resolveTelemetryPatch（80-83 行）——任何非空值（包括 '0'/'false'）都禁用：隐私开关宁可误关不可误开。组合里没有遥测行时开关自然满足，不产生补丁。

五层顺序定案：bundle 层 → profile 用户层 → home 用户层 → --patch overlay → 遥测开关。应用在空列表 [] 上，命中同 id 即整行替换。这就是整个 dsh 的「配置树」的全部真相。

§2runProfile：boot + 信号

212

createProcessShutdown（process-shutdown.ts）：有界关机的控制器——dispose 整棵树是它 shutdown 时执行的第一个动作。之后所有退出路径（信号、app 请求退出、one-shot 完成）都走它。

223-224

信号语义：SIGTERM 退出码 0（supervisor 的普通停止请求，launcher 不知道应用是否算完成）；SIGINT 退出码 130（用户中断）。信号在 boot() settle 之前就接管 teardown——注释解释：insert 的 provider 可能在兄弟行还没挂完时就 publish。

225

installFailLoud：boot 完成后的未处理 rejection 也不再静默——每个未处理错误都 dispose 树并报告。这是「错了就大声崩」原则的进程级实现。

243-248

composeLive 是热重组的补丁快照：bundle 层在底、overlay 在顶，用户的两个文件（profile 的 + home 的）每次重组都重新读盘。注意整体 structuredClone——见 §3。

251

调 03 页的 boot()。传的 patches 也是 structuredClone(allPatches(composed))——boot 应用补丁时不能 mutate 后续热重组要用的原对象。

258

prepare 回调（03 页的 prepare 参数）：provide 启动环境快照——在任何配置树条目挂载前，插件解析启动期环境值（DSH_* env 等）都从这同一个不可变来源读。

258

provide 命令行：内部参数（01 页的 args）+ exit 请求函数。任何注入的 app 插件都能读同一份不可变参数快照；one-shot 完成时通过 exit 请求关机。

282-287

HMR 补挂：web bundle 禁用了共享的模块重载 hmr 行（其 reload 生命周期未测试），所以这里补一个 root: [] 的 watch-only HMR 实例——只做「cordis.patch.yml 编辑即时生效」的配置热重载，不做模块重载。缺 timer 服务就先挂 timer（HMR 依赖它）。静默跳过会破坏文档承诺的热重载契约，所以宁可显式补挂。

288-293

两个 watch：profile 的 patch 文件和 home 的 patch 文件。文件一改，watchUserPatches 就用 composeLive 重算补丁、重组插件树。

§3composeLive：热重组的补丁快照

为什么 composeLive 和 boot 调用前都要 structuredClone？（这是全库最重要的 gotcha，02 页提过，这里看它的完整因果）：include 的 insert 行按引用 push 进挂载树，后续 id 定向补丁原地 mutate那些对象。如果复用同一份解析出的补丁对象，一次 boot 的覆盖就会「烤」进 bundle 的 in-memory insert 行——之后删除用户 override 也回不去了。每次应用前 clone，才能保证「删除 override = 回到 bundle 默认」。

热重组的完整机制：watch 发现文件变化 → composeLive() 重读两个用户文件 + 重新拼四层 → Loader 对差异行做「卸载旧的、挂载新的」→ 被换掉的插件 fiber 销毁，其全部注册逆转（服务、事件、effect）→ 新 fiber 挂载。进程不重启，配置即代码。

§4启动链完成：你拥有了一棵树

到这里，主干 A 走完了。回望这条链：

bin.ts（分派）→ args.ts（解析）→ loadProfile（发现 profile 与 bundle）→ composeEntries（五层补丁压成条目表）→ boot()（条目表挂成插件树）→ runProfile（信号 + 热更新 watch）。

现在 runProfile 返回 { ctx, shutdown }——ctx 就是那棵活树。树上有 78+ 个插件，其中一个叫 dsh-agent-loop。接下来的主干 B（05→14 页）就钻进这个插件的心脏，跟踪一条消息从进入 inbox 到工具结果落盘的每一步代码。

动手验证：pnpm dsh --profile web --dump-config 打印的就是这台机器实际会启动的条目表；在 $DSH_HOME/cordis.patch.yml 里改一行，长驻的 web 进程会即时重组。
