§1composeProfile：五层拼齐

229-231

prepareProfile（187-192 行）：先按需初始化（0.1.5 新增：fromDefaultProfile 非空时调 initializeProfileFromDefault），再调 02 页的 loadProfile，然后重写空根配置。注释解释为什么每次都要重写：Loader 的树写回（插件自卸载会持久化当前树）可能把组合好的行烤进 cordis.yml——下次 boot 就会重复每个 bundle 的 insert。所以根永远是空的。

232

healProfilesModuleFallback：02 页末提过的 symlink 补全。放在这里而不是 loadProfile 里，是因为它需要已解析好的 profile（含全部 bundle 层）才能算依赖闭包；而且它是 async 的（0.1.3-alpha.2 起重构为 async + 锁内更新）。

233

第③层：home 级 $DSH_HOME/cordis.patch.yml——机器级偏好，在 profile 层之后应用（高于它）。loadOptionalPatches：文件不存在就返回空（可选层）。

234

第④层：--patch overlay，按 argv 顺序。这里 overlay 只是被 load；真正 push 进 composedOverlays 是在 240 行复制之后——因为第⑤层遥测开关也要进 overlay，而用户 overlay 不能被污染。

237-239

四层压成一张表（第五层在 242 行并入）：同一个 composeEntries——与 boot 里的挂载用同一个算法，保证「flag 推导和配置 dump 看到的，就是实际挂载的」。

236-239

rows 是 id → Entry 索引，供 launcher 自己的行级检查（如 241 行查遥测行是否存在）。

241-242

第⑤层：遥测开关。resolveTelemetryPatch（profile-boot.ts:167-170）——任何非空值（包括 '0'/'false'）都禁用：隐私开关宁可误关不可误开。组合里没有遥测行时开关自然满足，不产生补丁。

§1binitializeProfileFromDefault：0.1.5 的模板初始化

0.1.5 之前，「用出厂模板创建一个新 profile」只有一条隐式路径：profile 目录不存在且名字恰好有模板时，loadProfile 自动初始化（02 页 820-828 行）。这带来一个尴尬——想以 web 为底稿建一个自己的 rescue profile 做不到，因为 rescue 没有模板，loadProfile 只会报错让你用 dsh plugin 从零建。

0.1.5 的 --from-default-profile <name> 补上了这条路径：dsh --profile rescue --from-default-profile web。

104-118

只复制模板的 bundle 列表与 reload 策略（93-98 行的 JSDoc 原文）：不读同名出厂 profile 的任何本地状态，也不持久化任何继承元数据。所以「从 web 派生」得到的是一份快照，不是一条持续跟随 web 变化的链接——后续 web 模板升级不会影响已建好的 profile（除了 normalizeShippedProfile 覆盖的历史元组规范化，见 02 页）。

119-124

出货名保留：--profile web --from-default-profile acp 被拒。理由很清楚——web 是出厂模板名，它的内容由安装方定义；让你用别的模板把它覆盖掉，等于让安装方的 profile 名不再可靠。想自定义就换个名字。

125-140

独占创建：mkdirSync(dir) 故意不加 recursive——目录已存在就抛 EEXIST。recursive: true 会静默成功，那样两个并发的 dsh --from-default-profile 就可能都以为自己是创建者。抛错后分两种情况报出不同的提示：已有 package.json（是个真 profile，别覆盖）vs 只有一个空目录（名字被别人占了）。

141-153

失败即回滚：initProfile 写文件到一半失败时，rmSync 把整个目录删掉——绝不留一个「有目录但没 package.json」的半成品（那会让下次 loadProfile 走进 02 页的自动初始化分支，行为难以预测）。连清理都失败时用 AggregateError 把两个错误一起抛出。

三条初始化路径的分工（0.1.5 起）：

  • 隐式——loadProfile（02 页 820-828 行）：名字有出厂模板 → 自动建。这是 dsh web 第一次跑就能用的原因。
  • 显式——initializeProfileFromDefault（本页）：用 任意出厂模板建一个自定义名字的 profile。这是新增能力。
  • 手动——dsh plugin --profile <name> add <package>：从零建，bundle 列表自己攒。

显式路径只作用于「目录还不存在」的那一次：prepareProfile 每次都先调它，但已存在的 profile 会让它抛错——所以 prepareProfile 的调用点必须先判存在性。看 188 行的实现：if (fromDefaultProfile !== undefined) initializeProfileFromDefault(...)，随后 loadProfile 的隐式分支自然不会触发。

§2runProfile：boot + 信号

295-298

createProcessShutdown（process-shutdown.ts）：有界关机的控制器——dispose 整棵树、再卸载代理。之后所有退出路径（信号、app 请求退出、one-shot 完成）都走它。

309-310

信号语义：SIGTERM 退出码 0（supervisor 的普通停止请求，launcher 不知道应用是否算完成）；SIGINT 退出码 130（用户中断）。这两行的注释解释：信号在 boot() settle 之前就接管 teardown——因为 insert 的 provider 可能在兄弟行还没挂完时就 publish。

311

installFailLoud：boot 完成后的未处理 rejection 也不再静默——每个未处理错误都 dispose 树并报告。这是「错了就大声崩」原则的进程级实现。

328-333

composeLive 是热重组的补丁快照：bundle 层在底、overlay 在顶，用户的两个文件（profile 的 + home 的）每次重组都重新读盘（316-322 行的注释解释：两个 watcher 各自只拿到「变化的那个文件」的补丁，重读两个文件才不会让它们互相缝进对方的陈旧副本）。注意整体 structuredClone——见 §3。

336

调 03 页的 boot()。传的 patches 也是 structuredClone(allPatches(composed))——boot 应用补丁时不能 mutate 后续热重组要用的原对象（334-335 行的注释：「与 composeLive 同一个 insert 别名理由」）。

340

prepare 回调（03 页的 prepare 参数）：provide 启动环境快照——在任何配置树条目挂载前，插件解析启动期环境值（DSH_* env 等）都从这同一个不可变来源读。

343-347

provide 命令行：内部参数（01 页的 args）+ exit 请求函数 + ready 就绪信号。任何注入的 app 插件都能读同一份不可变参数快照；one-shot 完成时通过 exit 请求关机。

355-358

watch 只在 patchReload === 'live' 时挂（02 页 86 行的 profile 声明）。启动即冻结的 profile（headless/acp/sdk）跳过这整段——350-354 行的注释说明这个取舍：它们照样应用所有用户层，只是不装 HMR 回退与 watcher。

366-371

HMR 补挂：dsh-base 默认禁用了模块重载的 hmr 行，所以这里补一个 root: [] 的 watch-only HMR 实例——只做「cordis.patch.yml 编辑即时生效」的配置热重载，不做模块重载。缺 timer 服务就先挂 timer（HMR 依赖它）。静默跳过会破坏文档承诺的热重载契约（363-365 行注释），所以宁可显式补挂。

372-381

两个 watch：profile 的 patch 文件和 home 的 patch 文件。文件一改，watchUserPatches 就用 composeLive 重算补丁、重组插件树。

382-384

suppressShutdownError（270-274 行）：watcher 安装期间的失败要分两种——树已经因为信号或 appExit 在退出（那这个失败是「如期退出」的副产品，吞掉）vs 真的装不上 watch（抛出）。判据是 signalShutdown.signal.aborted 加 fiber 状态。

386-390

就绪信号在最后才 commit：只有「没被信号打断 + fiber 仍 ACTIVE + loader 还在」三条件齐备，才通知应用「可以开始干活了」。这样应用不会在树还在重组、或者已经被要求退出的情况下开始服务。

§3composeLive：热重组的补丁快照

为什么 composeLive 和 boot 调用前都要 structuredClone？（这是全库最重要的 gotcha，02 页提过，这里看它的完整因果）：include 的 insert 行按引用 push 进挂载树，后续 id 定向补丁原地 mutate那些对象。如果复用同一份解析出的补丁对象，一次 boot 的覆盖就会「烤」进 bundle 的 in-memory insert 行——之后删除用户 override 也回不去了。每次应用前 clone，才能保证「删除 override = 回到 bundle 默认」。

热重组的完整机制：watch 发现文件变化 → composeLive()（328 行）重读两个用户文件 + 重新拼四层 → Loader 对差异行做「卸载旧的、挂载新的」→ 被换掉的插件 fiber 销毁，其全部注册逆转（服务、事件、effect）→ 新 fiber 挂载。进程不重启，配置即代码。

§4启动链完成：你拥有了一棵树

到这里，主干 A 走完了。回望这条链：

bin.ts（分派）→ args.ts（解析，含 0.1.5 的 --from-default-profile）→ initializeProfileFromDefault（按需用模板建 profile）→ loadProfile（发现 profile 与 bundle）→ composeEntries（五层补丁压成条目表）→ boot()（条目表挂成插件树）→ runProfile（就绪信号 + 信号处理 + 热更新 watch）。

现在 runProfile 返回 { ctx, shutdown }——ctx 就是那棵活树。树上有 78+ 个插件，其中一个叫 dsh-agent-loop。接下来的主干 B（05→14 页）就钻进这个插件的心脏，跟踪一条消息从进入 inbox 到工具结果落盘的每一步代码。

动手验证：pnpm dsh --profile web --dump-config 打印的就是这台机器实际会启动的条目表（0.1.5 起 --from-default-profile 也对这个 dump 生效，见 00 页 54 行）；在 $DSH_HOME/cordis.patch.yml 里改一行，长驻的 web 进程会即时重组。
