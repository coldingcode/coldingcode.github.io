§1这个文件在哪、怎么被调用

根 package.json 的 scripts 里有这样一行（package.json:136）：

"dsh": "node --import tsx/esm apps/cli/src/bin.ts"

所以 pnpm dsh web 实际执行的是 node --import tsx/esm apps/cli/src/bin.ts web。--import tsx/esm 让 Node 直接跑 TypeScript 源码（ESM-only hook）。这就是仓库里说的「dsh CLI source launch runs through tsx's ESM-only hook」——源码启动模式。

§3行级解读

1

shebang。这是可执行脚本的入口行——npm 发布的 bin 会以这个文件为命令入口。

9

/* v8 ignore file */：告诉覆盖率工具忽略本文件的测试覆盖——因为这个文件是「自执行的 dispatch」（模块加载即运行），真正的验收靠 built-bin acceptance 测试跑产物。

11-12

两个 node 内置 import：readFileSync 读版本号；fileURLToPath 把 ESM 的 import.meta.url 转成文件路径——ESM 里不能用 __dirname，这是替代手段。

13

loadLayeredEnv('dsh')：从 @deepseek-ai/dsh-app-boot 加载分层环境变量快照（后面在 runProfile 里被 provide 进插件树，见 04 页）。「layered」= 进程 env + 根 .env 文件按层合并。

14

parseDshArgs 来自 ./args.ts——注意是 .ts 后缀的相对导入（仓库约定：跨包用包名，包内用 .ts 后缀）。下一站（01 页）讲它。

17-22

readVersion：读自己包目录的 package.json 取 version 字段。new URL('../package.json', import.meta.url) 相对当前文件定位——注释解释为什么源码树（src/）和产物树（lib/）都坐在 apps/cli 下一层，所以这个相对跳转对两者都成立。

24

整个进程的第一行真实逻辑：解析 argv（去掉前两个：node 路径和脚本路径），拿到 invocation。这个函数的返回类型是判别联合 DshInvocation（01 页详述）。

26

顶层 await：ESM 模块顶层允许 await。switch 按 mode 分发。注意三种 mode 都是动态 import——这是设计决策，见 §4。

27-36

主路径 profile（dsh web / dsh --profile headless "task" 都走这）：动态 import profile-boot.ts，调 runProfile。传四个参数：环境快照、profile 名、--patch overlay 路径、以及「内部参数」（profile 名之后的所有东西，原样交给插件树）。这一调用最终长出一整棵插件树（02→04 页）。

37-41

plugin 模式：管理 profile 的插件依赖，转发给 pnpm。与主链无关，略过。

42-46

dump-config 模式：打印组装好的配置树然后退出，不真正 boot。它和主链共用 02 页的组装函数，所以值得知道它的存在。

48-49

穷尽性检查：invocation satisfies never 是 TypeScript 的编译期断言——如果将来 DshInvocation 加了新变体，这行会编译失败，逼你处理。AGENTS.md 里「switch 判别标签、closed union 以 assertNever 兜底」约定的第一种形态（这里是 satisfies 版本，效果相同）。

§4一个设计问题：为什么动态 import

为什么 runProfile/runPlugin/runDumpConfig 不静态 import，而要在 switch 里 await import()？文件头的 JSDoc 说了原因：

Dynamic imports per mode keep unrelated modes out of each dispatch path——每个 mode 的无关模块不进对方的派发路径。

如果静态 import 三个文件，那么无论你跑哪个 mode，Node 都会加载全部三个模块（以及它们的依赖树）。动态 import 让 dsh plugin 不需要加载 profile 启动链（含 Cordis Loader 等重依赖），也让 --help/参数错误的路径（在 parseDshArgs 里直接 process.exit）不碰任何重模块——帮助文本和报错要快。

从这里往下看主链：dsh web 的下一步是 profile 分支 → runProfile（04 页）。但在 runProfile 之前，先看 parseDshArgs 怎么把 argv 变成结构化的 invocation（01 页）——这是理解「launcher flags 与 app flags 的边界」的关键。
