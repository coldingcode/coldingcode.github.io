§1SessionEvent：信封

447-479

判别联合（不是独立 type/data 联合）：switch (event.type) 直接收窄 event.data。整个仓库的日志处理都靠这一点。

451

seq 契约：seq = 它进日志时的 log.length。这是全系统契约（§2 会看到落点）。

465

ignorable: true = 纯信息事件，不认识的读者可跳过。缺席 = 必需：遇到未识别且无标记的事件必须拒绝重建。设计取向：忘记打标记导致过度拒绝（不便），好过默默恢复一个被掏空的会话（灾难）。

466-476

surfaceOp/sourceEventSeqs 只存在于三个消息生产类型：user/message、assistant/message、tool/result。其他类型带这些字段会编译失败——append 签名里 T extends SurfaceEventType ? [opts: SurfaceIntent] : [] 强制。

§2append：唯一写入路径

709-712

无损 JSON 是第一道校验：snapshotJsonValue 一次递归读、校验、拷贝每个嵌套值——BigInt/函数/symbol/undefined/负零/非有限数/循环引用/稀疏数组/Map/Set/Date/类实例全部拒绝。一次遍历完成，带状态 getter 无法给校验和存储供不同值。

713

assertSupportedRequestHeader：request/header 的结构校验（header 的 config/system/tools 字段合法性）。

718-721

防重入：appending 标志——append 的发布边界打开时不允许再 append。谁可能重入？同步的 session/event 观察者里再调 append。

722-728

构造事件：seq = log.length（契约落点），data 用快照（不是调用者的原对象），然后 deepFreeze——进日志的值永远不可变，调用者改原对象不影响日志。

729

surfaceManager.validateNext：surface 一致性校验（§3）——在任何 mutation 之前，失败不留下半成品。

735-736

通知收集在 push 之前——同步观察者读到的是「日志尚未包含此事件」的状态。这就是 inbox 里「同步观察者看到 splice 前列表」的机制基础。

738-739

进内存日志 = 已提交。热路径不阻塞 I/O——持久化插件走 session/event + session/flush 异步缓冲。eventsSnapshot 失效，下次 getter 重建。

741

invokeContainedSessionObservers：观察者失败被逐 listener 隔离——一个坏的观察者不影响其他观察者看到同一事件，也不改变返回值。

744-748

finally 清理 appending 标志；若发布期间有人请求 detach，等 unwind 后执行——保证创建/销毁边界有序。

「进日志 = 已提交」是理解全库持久化的钥匙：append 返回后事件就是事实，磁盘写入是异步的。所以崩溃恢复靠 repair.ts 扫描日志尾部未闭合的 turn/step/工具调用，合成确定性的 tool/result（TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN）、step/end、turn/end（reason: interrupted）。

§3surface 校验：planSurfaceEvent

append 第 729 行的 validateNext 走 surface.ts（479 行）。核心是 planSurfaceEvent——先计划、再应用，计划失败不留下半成品：

341-343

seq 连续性在 surface 层强制：每个事件进 surface 前必须严格等于期望序号。这就是「seq 断裂整个系统会错」的第一道防线。

344-349

surfaceOp 校验（195-219 行的 surfaceOpOf）：非 surface 类型带 surfaceOp → 报错；surface 类型缺 surfaceOp → 报错（消息生产事件必须声明它如何进入 surface）。append 是普通路径。

350-352

replace 路径（compaction 用）：三个校验叠加——范围两端必须在当前 surface 里（replacementRange，246-266 行，含 start≤end）、sourceEventSeqs 必须包含每一个被遮蔽的节点（assertProvenance，211-243 行）、tool/result 的替换只能改 content（见下）。

306-329

assertToolResultRewrite 的精妙：把原始和替换的 tool/result 各复制一份、把 content 置 null 后深比较——相等才放行。即「除 content 外一切字段必须逐字节相同」。为什么这么严？surface 替换直接改变模型看到的历史，任何越界改写都可能让模型上下文失真。

§4构造器：seed 的校验

551-570

seed 走与 append 完全相同的校验：无损 JSON、信封、seq 必须从 0 连续。注释点明动机：replay/fork 不能构造出「任何持久化后端都存不了」的活日志——坏 seed 若不在入口拦截，会延迟成后端拒绝或内存/磁盘的静默分叉。

575

seed 也过 surface 校验（与 append 同一 validateNext）——候选在进 log 前计划，失败不部分 mutate surface。

582

firstLiveSeq = seed 长度：本次进程构造时点。它之前的 seq 来自构造（replay/fork/resume），从不经过 session/event 火线——所以 telemetry 这类「以重放代替订阅」的消费者从这里开始。

602-604

session/end-seed 标记：firstLiveSeq 的持久投影（空 payload 的 log-only 事件）。只写一次——seed 已以它结尾就不再标记，重复打开会话不会让日志每次 +1。读存储历史时取最后一个该事件（不一定等于当前 firstLiveSeq）。

§5deriveMessages 与 firstLiveSeq

第 09 页 buildRequest 会调 deriveMessages()，这里提前看它的缓存结构（index.ts:701-729）：

  • 投影规则是一个函数：deriveEventMessage（surface.ts:90-121）——user/message 原样返回；assistant/message 空内容返回 null（只为承载 max-tokens usage 的事件不进 transcript）；tool/result 返回 message；其他类型（边界、chunk、log-only）投影为 null。
  • 增量缓存：每个 surface 节点只投影一次（O(新节点)）；surface 重写（replace）使 replaceGeneration 变化，缓存重建。
  • 共享冻结：返回的数组每次是全新快照（后追加不会撑大已持有的数组），其中的 Message 对象与日志事件共享同一批深冻结对象——投递、持久历史、模型请求三界共用，无第二份深拷贝。

为什么模型历史必须来自日志投影？因为 09 页的 buildRequest 把 deriveMessages() 的结果直接放进请求。任何想给模型塞内容的路径都只能先 append 到日志。「模型可见 ⟺ 已记录」从一条纪律变成结构上不可能违反的约束——invariant 只负责断言它。
