目标与计划：跨轮次的持续任务与日志化的计划模式

目标（goal）是「同会话的持续任务」：agent 一轮做不完，goal 驱动它继续。计划（plan）是把「计划模式」做成持久状态：计划文档、审批、切换回执行模式，全部是可回放的状态。

(卷一连接点) 05 页 turn 循环 + agent/* 事件续跑 · 06 页 SessionEventMap 扩展 → 本域：goal / goal-round-driver / command-goal / tool-goal / plan-mode / plan → (回心脏) goal 续跑经 agent/* 事件回到 kick/turn

§3机制：goal 轮驱动与 plan 状态

  1. goal 的续跑：goal-round-driver 监听 agent/* 事件——一个 turn 结束后若 goal 未完成，它通过 agent 事件发起下一个轮次（05 页 turn-stopping 的「数据决定」之外的另一条续跑通道）。goal 是「同会话目标」，与 subagent 的「另开会话」相对。
  2. plan 是日志化的状态：进入计划模式 = 一个可回放的持久状态切换。PlanModeController 通过 tools + systemPrompt 注入切换模型的行为面（计划工具集 + 计划提示词）。
  3. 命令与工具双入口：用户 /goal（命令，23 页的旁路）与模型 tool-goal（工具）都能操作目标——同一能力、两个入口，这是 dsh 的常见形态。

§4关键代码

202-203

plan 模式 = 换工具面 + 换提示词面——它不碰 loop（05 页），只改「模型看到什么」（12 页的 systemPrompt 层与 14 页的 registry）。这是「插件不动循环」原则的标准示范。

19

goal-round-driver 的依赖面：agents（听事件/发起轮次）+ goals（状态）+ sessions（读日志判断完成度）。它站在心脏（05 页）的旁边驱动它。

§5易错点

「模型可见 ⟺ 已记录」对 plan 同样适用：计划状态必须可回放——所以 plan 是 logged state（进 SessionEventMap），不是内存变量。切换模式但没落盘 = 重启后模型行为与日志不一致。

goal 与 subagent 的分界：goal = 同会话的持续任务（22 页的对面）；subagent = 另开会话。选错机制是常见设计错误——判断标准是「结果是否要留在当前日志里」。
